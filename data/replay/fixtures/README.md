# Replay-harness fixtures

This directory holds local data fixtures the M2 replay harness reads at
runtime. Per Rule 26 (`CLAUDE_PREFLIGHT.md`), the LLM-model fork
**cannot query trader-prod's live DB at replay runtime**. The
documented exception path is exactly this: "use synthesized fixtures or
a deliberately-curated local sample DB."

Files in this directory are data, not code. They are:

- **Gitignored by default.** See `.gitignore` for the patterns.
- **Treated as snapshots in time.** Re-export when the replay window
  extends past the snapshot's coverage.
- **Generated by procedures documented here**, not by hand-edited.

---

## `sentiment.sqlite` — Haiku sentiment snapshot

**Source:** trader-prod's `sentiment` table on the gap-and-go VPS
(`5.161.199.155:/opt/trader/app/trading.db`).

**What it contains:** one row per (ticker, ts_et) that the live
sentiment pipeline scored. Columns: `ts_et`, `ticker`, `sentiment_score`,
`polygon_article_id`, `haiku_model_id`.

**Coverage:** depends on export date. The trader-prod sentiment table
started recording 2026-04-29; replays of dates before that have no
sentiment data even if the fixture is fresh.

### Export procedure (one-time, repeat when window slides)

> **This procedure runs from a SEPARATE gap-and-go-anchored Cowork
> session.** Rule 26 prohibits an LLM-model session from SSHing to the
> VPS or touching `/opt/trader/app/trading.db`. The export is a
> cross-fork data-handoff, executed entirely from the gap-and-go side,
> with the file then transferred to Godzilla via a non-SSH path.

#### Step 1 — From a gap-and-go-anchored session: extract the snapshot

```bash
# (Gap-and-go session, SSH'd to the VPS as the trader user)
ssh trader@5.161.199.155
cd /tmp
sqlite3 /opt/trader/app/trading.db <<'SQL'
.mode csv
.headers on
.output /tmp/sentiment_export.csv
SELECT ts_et, ticker, sentiment_score, polygon_article_id, haiku_model_id
FROM sentiment
WHERE ts_et >= '2026-04-29'
ORDER BY ts_et;
SQL

# Convert CSV -> SQLite fixture file in the schema the replay loader expects
sqlite3 /tmp/sentiment_export.sqlite <<'SQL'
CREATE TABLE sentiment (
    ts_et TEXT NOT NULL,
    ticker TEXT NOT NULL,
    sentiment_score REAL NOT NULL,
    polygon_article_id TEXT,
    haiku_model_id TEXT
);
CREATE INDEX idx_sentiment_ticker_ts ON sentiment(ticker, ts_et);
.mode csv
.import --skip 1 /tmp/sentiment_export.csv sentiment
SQL

# Sanity check
sqlite3 /tmp/sentiment_export.sqlite "SELECT COUNT(*) FROM sentiment;"
sqlite3 /tmp/sentiment_export.sqlite "SELECT MIN(ts_et), MAX(ts_et) FROM sentiment;"
sqlite3 /tmp/sentiment_export.sqlite "SELECT ticker, COUNT(*) FROM sentiment GROUP BY ticker ORDER BY COUNT(*) DESC LIMIT 10;"
```

Record the three sanity-check outputs in the session log so the
import side can verify a clean transfer.

#### Step 2 — Transfer to Godzilla via a non-SSH path

Pick one:

- **Hetzner Storage Box** (if configured): `rsync` the file to the
  user-side Storage Box; download from Godzilla's web browser to
  `C:\trading\LLM model\data\replay\fixtures\sentiment.sqlite`.
- **`scp` from a third machine** (e.g. the user's laptop): the laptop
  SCPs from the VPS, then copies to Godzilla over the LAN / USB.
- **Encrypted email or signed S3 presign URL**: same pattern, just
  different transport.

The crossing rule is: no SSH from the LLM-model session (Godzilla) to
the VPS. The export and the transfer must originate from the
gap-and-go side or a neutral third party.

#### Step 3 — Verify the imported fixture

```powershell
# (Godzilla — Cowork session anchored at C:\trading\LLM model\)
cd 'C:\trading\LLM model'
.\.venv\Scripts\Activate.ps1
python -c "import sqlite3; conn = sqlite3.connect('data/replay/fixtures/sentiment.sqlite'); cur = conn.execute('SELECT COUNT(*), MIN(ts_et), MAX(ts_et) FROM sentiment'); print(cur.fetchone())"
```

Compare the count + min/max ts_et to the values recorded in Step 1.
If they match, the fixture is good to use. If they differ, the
transfer corrupted something — re-do.

### Re-export trigger

Re-export when any of these is true:

1. The replay window's `end_date` is past the fixture's `max ts_et`.
2. The fixture is more than 30 days old AND the live system has been
   running (older sentiment data tends to drift in coverage as the
   trader-prod news pipeline gets updates).
3. The trader-prod sentiment schema has changed since the last export
   (verify by `sqlite3 /opt/trader/app/trading.db ".schema sentiment"`
   from the gap-and-go side and comparing against the local fixture's
   schema).

## `ticker_metadata.json` — per-ticker slowly-changing fields

Built locally by `data/replay/ticker_metadata.py::warm_metadata_cache`
on first replay run, refreshed per the 7-day TTL described in that
module. Not exported from trader-prod. Safe to delete; it will be
rebuilt on the next run.

---

## What is NOT in this directory

- LLM cache files. Those live at `.replay_cache/` at the repo root,
  separate from data fixtures.
- Replay output reports. Those land in `docs/reports/` per the design
  doc.
- Anything credential-bearing. Fixtures must be scrubbed of API keys,
  tokens, customer identifiers, etc. The Haiku sentiment scores
  themselves are derived data and safe.
