### What shipped

`run_replay` no longer raises `NotImplementedError` when `ReplayConfig.tickers == "watchlist"`. Instead it reads the watchlist from a JSON fixture (default `config/watchlist_dynamic.json`, where main.py's daily 08:30 ET refresh writes), coerces to `tuple[str, ...]`, and threads through to `build_day_state` like any other ticker tuple. This is the last functional gap in M2.2 — every CLI flag advertised in the design doc now works end-to-end.

### Implementation

```python
# data/replay/driver.py, replacing the NotImplementedError block
if config.tickers == "watchlist":
    resolved = read_watchlist_file(
        config.watchlist_path, max_age_days=365 * 100,
    )
    if not resolved:
        raise RuntimeError(
            "run_replay: ReplayConfig.tickers='watchlist' but no "
            f"valid watchlist found at {config.watchlist_path}. "
            "Either run the watchlist refresh job to (re)generate "
            "that file or pass an explicit ticker tuple via "
            "ReplayConfig.tickers."
        )
    tickers: tuple[str, ...] = tuple(resolved)
else:
    tickers = config.tickers_tuple
```

### Decision lock-ins

**Read the file, don't fetch live.** Two paths existed: `build_dynamic_watchlist(polygon_key, ...)` (live Wikipedia + Polygon, every replay run) vs. `read_watchlist_file(path)` (disk fixture, deterministic). Locked in the file path because replay reproducibility is the whole reason the harness exists — making each run hit live network breaks that. The watchlist file is already maintained by main.py's daily refresh; replay consumes it the same way it consumes the sentiment fixture.

**Bypass the staleness check.** `read_watchlist_file`'s default `max_age_days=7` would error if the file is more than a week old. For a replay against historical bars, this has no semantic meaning — the file's recency isn't pinned to the replay's date range. Passed `max_age_days=365 * 100` from the driver. A future sub-task could add a directory of dated watchlist snapshots if precision per replay date ever matters.

**Loud failure on missing file (Rule 18).** `read_watchlist_file` returns `None` on missing / malformed / empty payload. The driver converts that to a `RuntimeError` naming the configured path and pointing at two resolution paths: regenerate the file or pass explicit tickers. No silent fallback to a hardcoded default — that would be the failure mode this rule was written to catch.

### Failure semantics matrix (Rule 18)

| Input shape | Behavior |
|---|---|
| `tickers="watchlist"`, file exists with valid payload | resolved → tuple → flows through |
| `tickers="watchlist"`, file missing | `RuntimeError` naming `config.watchlist_path` |
| `tickers="watchlist"`, file malformed JSON | `read_watchlist_file` logs + returns None → `RuntimeError` |
| `tickers="watchlist"`, file present but empty watchlist field | `read_watchlist_file` returns None → `RuntimeError` |
| `tickers=("AAPL", "NVDA")` (explicit tuple) | `read_watchlist_file` NOT called; tuple flows through directly |
| `tickers=()` (empty tuple) | `ReplayConfig.__post_init__` already rejects with ValueError (unchanged) |

### What the replay harness can do now

End-to-end one-liner:

```bash
python scripts/replay_with_llm.py --start 2026-04-01 --end 2026-04-30 \
    --tickers watchlist --prompt-version v1.0 \
    --t1-backend haiku_stand_in --t1-model claude-haiku-4-5 \
    --t3-enabled --t3-sample-rate 0.5 --t3-max-dollars 50 \
    --base-portfolio
```

This:

1. Resolves "watchlist" from `config/watchlist_dynamic.json` (M2.2 #25).
2. Filters trading days via NYSE calendar — holidays excluded (M2.2 #24).
3. Per trading day: builds DayState, runs T1+T2 tick loop, applies fills, runs T3 labeling pass with budget, runs base-strategy parallel pass — all with per-phase wall-clock instrumentation (M2.2 #23).
4. Persists every decision (live_merged, base, t3_only) with `regime` and `tier_provenance` columns (M2.2 #21, #22).
5. Aggregates cache stats + timing into `replay_runs.summary_json` (M2.2 #23).
6. Generates a 7-section markdown comparison report:
   - § 1: Run metadata + Cache stats table + Phase timing breakdown (M2.2 #23).
   - § 2: Decision summary by source × action.
   - § 3: Portfolio performance per side.
   - § 4: Divergence analysis (LLM vs base disagreement buckets).
   - § 5: LLM-specific quality (confidence histogram, setup labels, reasoning length).
   - § 5b: Per-(regime, source) trade count / win rate / total + avg realized P&L (M2.2 #22).
   - § 5c: Crash-period replay stub (intentionally not a per-run section).
   - § 5d: T1↔T3 agreement rate + 3×3 confusion matrix + disagreement P&L + confidence-band breakdown + tier_provenance counts (M2.2 #21).
   - § 6: Failure modes.
   - § 7: Top decisions worth manual review.
