### What shipped

The replay-harness comparison report's § 5d, previously a deferred stub that said "no per-tier persistence yet," now renders five real sub-blocks driven by the rows persisted in `replay_decisions`.

**`_section_5d_tier_agreement(conn, run_id) -> list[str]`** — composes the section from five sub-blocks:

1. **5d.1 Evaluated-pair denominator + tier failure tally.** Counts T1 (live_merged) and T3 (t3_only) failure-marker rows separately, then INNER JOINs the non-failure rows on `(run_id, ticker, tick_et)` to build the pair set. Failure markers excluded from the matrix: `setup_label` in `(schema_invalid_t1, api_failure_t1, t1_unexpected)` on T1, or `(schema_invalid_t3, api_failure_t3, t3_unexpected)` / `tier_provenance='t3_failed'` on T3.

2. **5d.2 Overall agreement rate + 3×3 confusion matrix.** Diagonal sum / total pairs. Matrix rendered as markdown 3×3 (rows = T1 action, cols = T3 action, all 9 cells populated with 0 if absent).

3. **5d.3 Disagreement profitability (T1 side).** For pairs where T1 and T3 disagreed: count disagreements, count with attached fills (via `replay_fills.realized_pl` join on T1's `decision_id`), report mean T1-side realized P&L. Explicit note that T3 has no portfolio simulation (it's a labeling pass), so a counterfactual T3 P&L is not computed.

4. **5d.4 Agreement by T1 confidence band.** Threshold = 75 (matches `escalation_rule.confidence_ceiling`). Two-row table: High (≥75) vs Low (<75), with N and per-band agreement rate. Renders `*(no data)*` when a band is empty.

5. **5d.5 Tier 2 escalation tier_provenance counts.** GROUP BY `tier_provenance` on live_merged rows. Counts table renders any of the enum values present (`t1_only`, `t1_t2_agree`, `t1_t2_disagree`, `t1_fallback_t2`, `t1_only_budget_exhausted`, `t1_failed`) plus `*(none)*` for NULL. Explicit note that the design doc's T2-confirm-vs-reverse P&L analysis is out of scope — requires persisting the pre-merge T1 action, which today is not stored.

Render path in `generate_report`: section 5 → 5b stub → 5c stub → **5d real** → section 6.

### Persistence extension (in-scope side change)

The original 5d.5 design depended on `tier_provenance` being available on live_merged rows. The existing `_write_portfolio_side` did NOT persist this column (only the t3_only insert at sub-task #20 did), so live_merged rows in real runs landed with NULL `tier_provenance` regardless of what the LLMDecision carried.

Three-line extension to the live_merged/base INSERT statement:

```python
"INSERT INTO replay_decisions "
"(run_id, trading_date, tick_et, ticker, decision_source, "
" action, setup_label, confidence, reasoning, "
" tier_provenance) "
"VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)",
(..., td.decision.tier_provenance),
```

For base rows, `LLMDecision.tier_provenance` is always None (base never goes through merge.py), so base rows still land with NULL — no behavior change there. Existing test_persistence assertions that didn't query the column are unaffected.

New test `test_write_day_live_merged_persists_tier_provenance` verifies a live_merged row with `tier_provenance="t1_t2_agree"` is preserved through the persistence write.
