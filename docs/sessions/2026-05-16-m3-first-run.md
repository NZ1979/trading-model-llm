## Findings

### 1. The single LLM trade lost $19.32

MSFT on 2026-05-15 at 10:45 EDT. LLM said Buy; base said Hold (no fill).
This is the entirety of § 4 divergence. Not enough data to draw any
signal-quality conclusion from one trade.

### 2. The LLM is uniformly unconfident — biggest finding

| Confidence | Count | % |
|---|---|---|
| 0–19 | 238 | 13.7% |
| 20–29 | 1,189 | **68.3%** |
| 30–39 | 294 | 16.9% |
| 40–49 | 20 | 1.1% |
| 50+ | 1 | <0.1% |

Median ~25. Max 55. The T2 escalation band starts at 50, so only **one**
decision in the whole week even approached it. This explains the zero T2
escalations cleanly: there was nothing to escalate.

This is honest from the model's perspective (large-caps in a quiet week
with no sentiment context — there genuinely isn't a high-conviction
signal). But it also means the T1↔T2↔T3 architecture is functionally
collapsing to T1-only on this kind of input.

### 3. Setup label sprawl — design-level issue

§ 5's `setup_label` frequency table is **925 lines long** (report lines
103–1027). The LLM is generating freeform setup descriptions like
"Late-day exhaustion, 5min to close" and "EOD consolidation, insufficient
setup" rather than picking from a fixed enum. Each unique string is
counted separately, so the table is basically uncountable.

This breaks aggregation entirely. You can't bucket ~900 unique labels for
analysis or for the failure-pattern matching in § 6.

### 4. T1 schema failures: 2 of 1,742 (0.11%)

Haiku returned malformed JSON twice. Synthetic Holds with
`setup_label="schema_invalid_t1"` emitted per Rule 18 fail-loud. Provenance
column = `t1_failed`. No silent degradation. Worth a one-time grep of
`docs/sessions/2026-05-16-m3-first-run.log` to capture what Haiku actually
returned in those two cases.

### 5. § 5b regime + § 5d tier_provenance both populated correctly

§ 5b: 1 trade, `bull` regime, 0% win rate. The M2.2 #22 regime classifier
runs end-to-end.

§ 5d tier_provenance counts:

### 6. Tick loop dominates runtime

Phase timing breakdown:

- Tick loop: 16m 35s mean/day × 5 days = **99.7% of wall clock**

~12 sec per RTH tick on average. Acceptable for replay; orders of magnitude
too slow for live. If/when live deployment is on the table, parallelizing
Haiku calls across candidates per tick is the obvious optimization.

## Follow-ups for future M3 sessions

Captured here as candidates for sub-tasks; none are blocking the next M3
run.

1. **Setup label enum (or post-hoc bucketing).** Either constrain
   `setup_label` to a small enum in the prompt schema (cleanest), or have
   the report bucket-classify freeform strings into a handful of
   categories before tabulating § 5. Without one or the other, § 5 is
   unreadable on any non-trivial run.

2. **`--quiet-missing-sentiment` flag** or per-day aggregate stat. With an
   empty sentiment fixture the harness emits one WARNING per (article ×
   ticker) lookup. The 5-day × 5-ticker run produced thousands of
   identical-shape warnings, drowning out any other signal in the log.
   Real fixtures will reduce this, but the harness should aggregate
   missing-sentiment counts at end-of-day even with full fixtures, not
   per-line warn.

3. **Real sentiment fixture export.** Open a gap-and-go-anchored Cowork
   session and run the procedure in `data/replay/fixtures/README.md` §
   "Export procedure". Without sentiment data, the divergence section,
   the sentiment-informed branches of `evaluate_trade`, and any
   correlation between confidence and news context cannot be evaluated.

4. **Wider replay window or different universe.** 5 days × 5 large-caps
   generated 1 trade — not enough to evaluate signal quality. The next
   run needs either (a) a month-long window for more trade samples, (b)
   more tickers in the same large-cap universe, or (c) a deliberate
   universe-experiment swap to the existing `watchlist_dynamic.json` (500
   Russell 2000 momentum names) to see whether the LLM's edge tracks the
   base codebase's small-cap setup universe or whether it differs.

   **Framing correction (added post-commit `55bf724`):** the LLM model
   replaces the *signal engine*, not the *universe*. Per
   `docs/LLM_MODEL_CHARTER.md`, the premise is that an LLM makes better
   Buy/Sell/Hold decisions on the same candidate stream the rule-based
   gap-and-go strategy sees (same pre-filter, same watchlist style). The
   base codebase's edge lives in small-cap momentum because that's where
   gap-and-go was designed for; whether the LLM model's edge lives there
   too, or in some other slice (large-caps, regime-stratified subsets,
   different sectors), is an **open empirical question** that M3 is
   supposed to help answer. Don't pre-suppose the universe — pick the
   next window as a deliberate experiment.

5. **Confidence calibration vs. escalation floor.** If 99% of T1 decisions
   land below 50, either the prompt is producing low-confidence outputs
   even when conviction is warranted (prompt issue), or the escalation
   floor of 50 is mis-calibrated against what Haiku actually emits. Worth
   checking once a larger run produces a representative distribution.

6. **Investigate the 2 T1 schema failures.** Grep the run log for the two
   `schema_invalid_t1` lines, capture the raw Haiku response shape, and
   decide whether to (a) loosen the schema validator, (b) add a JSON
   repair step, or (c) leave as-is since 0.11% is acceptable noise.
