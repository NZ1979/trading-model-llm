# Bug C patch — 2026-04-30

## What it fixes

Every Buy/Sell decision the platform produced today was rejected by Alpaca
with HTTP 422 "bracket orders require take_profit.limit_price". The platform
sent `order_class="bracket"` with only a `stop_loss` leg — but Alpaca's
bracket orders require BOTH `take_profit` AND `stop_loss` (3-legged OCO).

The author's intent (per the comment in the original code) was "entry +
single stop_loss child leg, no take_profit." That intent maps to Alpaca's
`order_class="oto"` (one-triggers-other), not `"bracket"`.

## Empirical verification

- Bug C reproduced via `/tmp/test_bracket_order.py` on the VPS:
  Alpaca returned `{"code": 40010001, "message": "bracket orders require
  take_profit.limit_price"}`.
- Fix verified via `/tmp/test_oto_order.py` on the VPS: Alpaca accepted
  `order_class="oto"` with `stop_loss` only, returning HTTP 200 with one
  child leg. Order canceled cleanly via DELETE (HTTP 204).

## What changed

Single source file: `execution/alpaca_orders.py`.

- `"order_class": "bracket"` → `"order_class": "oto"` (1 line).
- Comment block updated to explain the OTO semantics and reference this
  bug fix.

No other code paths reference `"bracket"` as an `order_class` string. The
function is still named `submit_bracket_order` (unchanged) because it's
still a multi-leg order submission, just with the correct order class.

## What this fix does NOT do (deferred to follow-up)

**Bug D — error body capture.** The production code calls `resp.raise_for_status()`
in `_post()` BEFORE reading the response body. That's why we couldn't see
Alpaca's actual rejection reason ("bracket orders require take_profit.limit_price")
from production logs and had to write a separate diagnostic script to capture it.

Recommended follow-up: rewrite `_post` to read the body before raising, and
include the body in the error string passed back to `submit_bracket_order`.
This is a Rule 16 issue ("Fail loud, never silent") but not blocking trading.
